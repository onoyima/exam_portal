1. PROJECT OVERVIEW
================================================================================

  Project Name:  Veritas Exam Portal (NextGen Assessment Portal)
  Location:      C:\xampp\htdocs\exam_portal
  Purpose:       A secure, AI-proctored digital examination system supporting
                 multiple exam types (Objective/MCQ, Practical/OSCE, VIVA/Oral)
                 with real-time proctoring, device authorization, and
                 comprehensive reporting. Built for Veritas University, Abuja.

  The system features:
  ─────────────────────
  - Multi-role system: Admin, Examiner (Staff), and Student
  - Three exam formats: Objective (MCQ), Practical (OSCE), VIVA (Oral)
  - 7-layer security stack including browser lockdown, AI face detection,
    device whitelisting, session hardening, and fullscreen enforcement
  - Real-time proctoring with live video (WebRTC)
  - Secure Exam Browser (Electron-based kiosk)
  - Staff chat system (private & group messaging)
  - Comprehensive audit trail for all CRUD operations
  - Analytics dashboard with Chart.js visualizations
  - CMS/Portal customization system
  - exeat2 (LMS) integration capabilities
  - Dark mode support

5. AUTHENTICATION & AUTHORIZATION SYSTEM
================================================================================

  5.1 ROLES (3-tier)
  ──────────────────────────────────────────────────────────────────────────────
  Role        Access Level
  ──────────────────────────────────────────────────────────────────────────────
  admin       Full system access: all admin pages, user management, exam CRUD,
              analytics, audit trail, proctoring, chat, settings
  examiner    Assessment/grading access only: assess students, view assigned
              exam results, staff chat
  student     Exam-taking access only: dashboard, objective exam engine,
              view results
  ──────────────────────────────────────────────────────────────────────────────

  5.2 AUTHENTICATION FLOW
  ──────────────────────────────────────────────────────────────────────────────
  STAFF LOGIN (login.php):
    1. Username + password form submission
    2. bcrypt verify against examiners table
    3. Legacy plaintext auto-upgrade: if plaintext matches, hash and update
    4. Session creation with role, user, examiner_id
    5. Login history audit log INSERT
    6. Redirect based on role (admin -> admin_dashboard, examiner -> assess)

  STUDENT LOGIN (student_login.php):
    1. Two-step AJAX process
    2. Step 1: Matric number lookup (cleaned: removes /,-, spaces)
    3. Identity confirmation modal displayed
    4. Step 2: Optional password verification (configurable via system_settings)
    5. session_regenerate_id(true) for session fixation prevention
    6. Session ID stored in students.current_session_id
    7. Multi-session detection: stored session ID compared on every proctor ping
    8. Login history INSERT

  5.3 SESSION HARDENING
  ──────────────────────────────────────────────────────────────────────────────
  - Current session_id stored in students.current_session_id at login
  - On every proctor_ping.php call, stored ID is compared to current session_id
  - If mismatch (another login from elsewhere), student is FORCED_LOGOUT
  - Inactivity timeout configurable via SESSION_LIFETIME (default 1800s/30min)
  - session_regenerate_id(true) on each student login

  5.4 AUTHORIZATION GATE
  ──────────────────────────────────────────────────────────────────────────────
  - Function: check_auth(array|string $allowed_roles)
  - Called on every protected page
  - Checks $_SESSION['role'] against allowed roles
  - On failure: redirects to appropriate login page based on requested access
  - Student routes additionally call check_device_auth()

  5.5 CSRF PROTECTION
  ──────────────────────────────────────────────────────────────────────────────
  - Token generation: bin2hex(random_bytes(32))
  - Stored in $_SESSION['csrf_token']
  - Validated on all POST requests via validate_csrf()
  - Hidden input generated via csrf_field() helper
  - Constant-time comparison via hash_equals()

  5.6 DEVICE AUTHORIZATION (check_device_auth())
  ──────────────────────────────────────────────────────────────────────────────
  - IP-based device registration and whitelisting
  - Auto-registers unknown IPs as 'pending' status
  - 'approved' devices: full access granted
  - 'rejected' devices: blocked with 403 + styled error page
  - 'pending' devices: shown waiting page with 15-second auto-refresh
  - Admin manages via admin_devices.php

8. EXAM TYPES & WORKFLOWS
================================================================================

  8.1 OBJECTIVE (MCQ) EXAMS
  ──────────────────────────────────────────────────────────────────────────────
  WORKFLOW:
    1. Admin creates exam via admin_objective_exams.php
       - Sets name, session, duration, max_attempts, grading method
       - Configures proctor flags (webcam, fullscreen, tab lock, etc.)
       - Sets scheduling (start_time, end_time)
       - Configures question pool (questions_to_show), shuffle settings
    2. Admin adds A/B/C/D questions via admin_objective_questions.php
       - Supports question text + optional image
       - Each option can have text + optional image
       - Correct answer marked (A/B/C/D), mark value assigned
    3. Admin assigns students to exam via admin_assign_students.php
       - Manual selection, bulk assign all, or filter by exeat2 criteria
    4. Student logs in, sees exam on dashboard
    5. Student clicks "Start Exam" -> enters student_objective_exam.php
    6. Questions rendered with navigation palette (grid)
    7. Answers saved via AJAX (objective_exam_api.php -> save_answer)
    8. Timer counts down, auto-submits at zero
    9. Proctor heartbeat (proctor_ping.php) runs every few seconds
    10. Violations tracked (tab blur, window switch, face detection)
    11. On submit/timeout: score calculated, attempt finalized
    12. Results viewable: per-attempt scores, time taken, review mode

  GRADING METHODS:
    - Highest: final grade = max score across all attempts
    - Average: final grade = average of all attempt scores

  SCORING POLICIES:
    - Highest attempt counts
    - First attempt counts
    - Last attempt counts

  TIMING: duration_minutes per attempt, with auto-finalize on expiry

  8.2 PRACTICAL (OSCE) EXAMS
  ──────────────────────────────────────────────────────────────────────────────
  WORKFLOW:
    1. Admin creates exam via admin_exams.php
    2. Admin adds procedural/assessment questions via admin_questions.php
       - Each question has text and score_values (e.g., "0,0.25,0.5,0.75,1")
    3. Examiner assigned to exam
    4. Examiner opens asses.php, selects exam
    5. Examiner searches for student by name/matric
    6. Examiner rates each procedure/step with score dropdown
    7. Scores saved instantly via AJAX to answers table
    8. Aggregate score calculated automatically (sum of all question scores)

  8.3 VIVA (ORAL) EXAMS
  ──────────────────────────────────────────────────────────────────────────────
  - Similar workflow to Practical exams
  - Categorized as 'viva' type in exams table
  - Results viewable separately from practical scores
  - Examiner rates student performance on oral criteria
  - Dedicated admin_viva_exams.php for management

20. LMS INCLUSION PLAN & RECOMMENDATIONS
================================================================================

  This section provides a strategic roadmap for integrating the Exam Portal
  with a Learning Management System (LMS) such as Moodle, Canvas, Sakai, or
  the existing exeat2 portal.

  20.1 CURRENT STATE
  ──────────────────────────────────────────────────────────────────────────────
  The portal currently operates as a standalone examination system with:
  - Its own student database (can import from exeat2)
  - Its own exam/question management
  - Its own authentication system
  - Manual synchronization scripts for exeat2
  - No standardized LMS interoperability (no LTI, SCORM, xAPI)

  20.2 INTEGRATION ARCHITECTURE OPTIONS
  ──────────────────────────────────────────────────────────────────────────────

  OPTION A: LTI 1.3 STANDARD INTEGRATION (RECOMMENDED)
  ──────────────────────────────────────────────────────────────────────────────
  Implement the portal as an LTI 1.3 Advantage tool provider:
  - Allows launching exams directly from any LTI-compliant LMS
  - Automatic user provisioning (no separate login needed)
  - Grade passback to LMS gradebook
  - Names and Roles Provisioning (membership sync)
  - Deep Linking for exam selection within LMS

  Required development:
    * LTI 1.3 tool provider library (e.g., 1EdTech's PHP SDK or opensource)
    * JWKS endpoint for public key distribution
    * OAuth 2.0 / OpenID Connect login flow
    * Grade passback endpoint (line items & scores)
    * Names and Roles Provisioning service
    * Deep Linking service

  OPTION B: SINGLE SIGN-ON (SSO) WITH SAML/OAUTH
  ──────────────────────────────────────────────────────────────────────────────
  Replace the existing login system with SSO:
  - SAML 2.0 SSO (works with most enterprise LMS)
  - OAuth 2.0 / OpenID Connect (modern approach)
  - CAS (Central Authentication Service)
  - Benefits: unified login, no separate credentials, automatic account creation

  OPTION C: CUSTOM REST API FOR LMS
  ──────────────────────────────────────────────────────────────────────────────
  Build a comprehensive REST API:
  - Course/exam sync endpoints
  - Student enrollment sync
  - Grade passback
  - Attendance tracking
  - Would need custom LMS plugins on the other side

  OPTION D: FULL EXEAT2 MERGER
  ──────────────────────────────────────────────────────────────────────────────
  Deep integration with the existing exeat2 Laravel portal:
  - Shared authentication
  - Single database for students
  - Course/semester sync
  - Result pushback to exeat2
  - Already partially implemented (import scripts exist)

22. SECURITY CONSIDERATIONS
================================================================================

  Current Security Measures:
  ──────────────────────────────────────────────────────────────────────────────
  ✓ SQL Injection Prevention: PDO prepared statements throughout
  ✓ XSS Prevention: htmlspecialchars() output encoding
  ✓ CSRF Protection: 32-byte random tokens validated on all POST
  ✓ Password Hashing: bcrypt with auto-upgrade from legacy plaintext
  ✓ Session Fixation Prevention: session_regenerate_id(true) on login
  ✓ Session Hardening: session ID stored in DB, concurrent login detection
  ✓ Device Authorization: IP-based whitelist with pending/approved/rejected
  ✓ Browser Lockdown: F12, right-click, keyboard shortcuts blocked
  ✓ Fullscreen Enforcement: API request fullscreen on exam start
  ✓ Violation Tracking: automatic lock on 5+ violations
  ✓ Audit Trail: all CRUD operations logged with before/after values
  ✓ Error Handling: no error details exposed to users, logged server-side
  ✓ HTTPS Required: camera/microphone access requires secure context
